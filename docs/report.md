# signal-watch-poc 報告書

- 期間: 2026-10-13〜2026-10-17
- 状態: **終了**(リポジトリはアーカイブ済み・読み取り専用)

## 結論

**既製品と比べて、この PoC に優れている点は無い。サービスへの発展は見送り、PoC を終了する。**

公開 Web ページの更新を自動で検出し、変更箇所を分かりやすく提示する仕組みは、試作として端から端まで動いた。
しかし、同じことは既製のサービス・ツール(下の「既製品との比較」)で、より少ない手間で、より広い範囲に実現できる。
この PoC ならではの利点は、利用者にとっての価値として既製品を上回るものではなかった。
予定していた4週間の評価(2026-10-19〜11-15)は、結論が出たため行わない。

## 目的(要件定義より)

- 複数の Web サイトを巡回するときの、更新の見落としと確認の手間を減らす
- 対象を限定して実用性を検証し、情報収集の効率化につながるサービスへ発展させられるかを判断する材料を得る

## 作ったもの

| 項目 | 内容 |
|---|---|
| 監視対象 | デジタル庁サイトの4ページ(新着一覧と、更新告知の多い個別ページ3件)。公共データ利用規約(第1.0版)・robots.txt を確認済み |
| 取得 | robots.txt の確認、同一ドメインに 5 秒以上の間隔、条件付きリクエスト(ETag / Last-Modified)、失敗時の間隔延長 |
| 変更検出 | 比較範囲(CSS セレクタ)の抽出と除外、行単位の差分。一覧ページは「追加だけ」を変更とみなす。行数の急減はページ構造の変化として失敗扱い |
| 保存 | `snapshots` ブランチに対象ごとに1コミット(出典表示付き)。履歴は1か月で整理 |
| 通知 | Slack(Incoming Webhook)に抜粋・差分へのリンク・元のページへのリンクを送る。取得失敗が続いたとき・回復したときも通知 |
| AI 要約 | Claude Code のヘッドレスモードをサブスクリプション認証で実行(従量課金なし)。モデルは Claude Opus 5.5 |
| 実行基盤 | GitHub Actions の定期実行(1日4回)。サーバ費用なし |
| 実装 | Python 3.13(uv・ruff・mypy strict・pytest)。テスト 97 件 |

技術選定の根拠は ADR-0001〜0004(`docs/adr/`)、要件・設計は Notion の要件定義・基本設計にある。

## 確かめたこと(2026-10-17)

- GitHub Actions から4ページを取得し、初回スナップショットを保存できた
- 変更を検出してコミットし、Slack に【変更】の通知(抜粋・差分リンク付き)が届いた。リンクから差分画面・元のページに移れた
  (新着一覧のスナップショットから1件を消す手作業で変更を作って確かめた)
- テスト通知に AI 要約が載り、内容も正しかった。claude.ai の追加使用量はオフで、追加料金は発生していない
- 定期実行(1日4回)を開始した

確かめていないこと: 実際のサイト更新による変更通知の精度(検出漏れ・誤検知)、確認の手間がどれだけ減るか。評価期間を行わなかったため。

## 既製品との比較

2026-10-17 時点の、筆者(Claude)の知識に基づく比較。各製品の機能・料金は公式サイトで確かめていない。

| 種類 | 例 | この PoC の機能との重なり |
|---|---|---|
| ページの変化を監視するサービス | Visualping、Distill.io、ChangeTower、Wachete、PageCrawl.io、Fluxguard、Versionista | 範囲指定・除外・差分・通知・履歴をすべて持つ。Visualping は変更の AI 要約もある。見た目(スクリーンショット)の比較、ログインが要るページなど、PoC に無い機能も多い |
| RSS の無いページから RSS を作るもの | RSS.app、FetchRSS、PolitePol、Feed43、RSSHub、Feedly | 一覧ページの新着の検知はこれで足りる |
| 自分で動かす OSS | changedetection.io、urlwatch、Huginn | changedetection.io は PoC の機能のほぼすべて(CSS / XPath の範囲指定、除外、差分の履歴、Slack などへの通知、JavaScript が必要なページ)を持ち、無料で自分で立てられる |

この PoC にしか無い点と、それが優位にならない理由:

| PoC の特徴 | 優位にならない理由 |
|---|---|
| サーバ費用ゼロ(GitHub Actions とサブスクリプションの範囲) | 既製品にも無料枠があり、changedetection.io は手元で無料で動く。対象を増やすと Actions とサブスクリプションの枠の制約が先に来る |
| 変更の記録が Git に残り、公開して共有できる | 既製品にも変更履歴と差分表示がある。公開の共有は利用者の需要として確かめていない。履歴は1か月で消える設計にした |
| 日本語の AI 要約 | Visualping などにも AI 要約がある |
| robots.txt・出典表示への配慮を処理に組み込んだ | 利用者にとっての機能ではなく、運用側の責任。既製品でも設定と運用で同じことができる |
| 官公庁のページ向けの調整(セレクタ、一覧の「追加だけ」判定) | 既製品でも範囲指定と除外の設定で同じことができる |

## 学んだこと

- **作る前に既製品を調べるべきだった。** 要件定義の段階で既製品との比較をしていれば、短い時間で同じ結論に着けた。次の PoC では、要件定義に「既存の手段・既製品との比較」を入れる
- 公開情報の自動取得では、利用規約・robots.txt・出典表示の確認が最初に要る。デジタル庁は公共データ利用規約で、取得・加工・公開がしやすかった
- 実際のページでは、HTML ソースの改行・リンクの中のブロック要素・一覧の押し出しなど、差分のノイズになる要素が多い。テキストの正規化と比較範囲の決め方が精度を左右する
- Claude のサブスクリプションで AI を自動実行するときは、API キーの環境変数が優先されて従量課金になる落とし穴がある。環境変数を渡さない・認証方式を確かめる、の二重の対策が要る

## 後片付け

- 定期実行(Watch・Prune snapshots)は止めた。リポジトリはアーカイブして読み取り専用にした
- GitHub の Secret(`SLACK_WEBHOOK_URL`・`CLAUDE_CODE_OAUTH_TOKEN`)は削除した
- 利用者が行うこと: Slack アプリ(signal-watch-poc)の削除。`claude setup-token` で発行した長期トークンは、無効化できるなら無効化する(方法はこの PoC では確かめていない。有効期限は発行から1年)
- `snapshots` ブランチ(取得したテキストと変更の記録)は、記録として残している。内容はデジタル庁のコンテンツを公共データ利用規約に基づき加工したもので、出典はブランチの README と各ファイルの先頭にある
